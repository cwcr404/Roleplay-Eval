# 芽衣知识库检索架构(knowledge architecture)

> 属于:Roleplay-Eval · 芽衣(角色扮演评测框架参考实现)
> 定位:讲解芽衣的「认知外挂层」——**攻略知识(V1)与背景叙事(V2)如何被检索、注入、隔离**,
> 以及**为什么 v0.1 用查表/模块加载、未来如何无痛切向量**。
> 这也是你 GitHub 开源报告里「可扩展性设计」的决策依据。

---

## 1. 几句话讲清架构

芽衣的稳定由**两层**支撑,这一份文档讲的是「认知层」:

```
用户输入
   │
   ▼
Agent1 意图路由 ──判断:闲聊 or 攻略──────────────┐
   │                                             │
   └────────────┬──────────────────────────────  │
                ▼                                │
   ┌──────────────────────┐   ┌──────────────────────┐
   │ V1 攻略知识库(工具)   │   │ V2 背景叙事库(身份)    │
   │ 标签/条目查表         │   │ 主题/维度整块加载      │
   └──────────┬───────────┘   └──────────┬───────────┘
              └────────────┬─────────────┘
                           ▼
                 Agent2 角色化(人格常量 + 注入的知识事实)
                           ▼
                  Agent3 / Judge(质检 / 评分)
```

**一句话:V1 管「芽衣知道怎么玩」,V2 管「芽衣记得自己是谁走过的路」;两者物理隔离,
通过检索接口独立注入 Agent2,互不串味。**

---

## 2. 两个知识库为什么必须分开

| | V1 攻略库 | V2 背景库 |
|---|---|---|
| 数据性质 | 工具知识(App 属性) | 角色叙事(人格属性) |
| 内容形态 | 标签化的数据字典(角色/圣痕/配队) | 连贯的人物事件叙事(家世/乐土/羁绊) |
| 本质回答 | 「怎么做 / 是什么」 | 「她是谁 / 她有过什么」 |
| 隔离理由 | 攻略数据**不该定义人格** | 人格叙事**不该混进攻略口径** |

**隔离是硬约束**,不是偏好:
- 攻略条目(如「真理之钥是理之律者的毕业武器」)绝不能反噬为"芽衣身份"讨论;
- 背景叙事(如"雷电女王觉醒")绝不能变成攻略里的角色强度话术。
- 因此 V1、V2 走**两套独立检索器、两个独立索引**,各自 return 各自的内容域。

## 3. v0.1 为什么用「查表 / 模块加载」而不是向量库(关键决策)

这是本报告最重要的决策点。**我们刻意不在 v0.1 上向量库**,理由如下:

### 3.1 数据规模不足以体现向量优势
- 当前 V1 ≈ 4.6KB(~19 条)、V2 ≈ 8.7KB(~23 块),合计 < 15KB。
- 向量的检索优势要在**千条量级、海量 + 语义模糊**场景才体现。这个体量下,
  查表在精度、速度、可复现性上都已够用,且**零外部依赖、零成本、数据不出机器**。

### 3.2 数据形态天然不适合「碎片化向量召回」
- V1 已打好 `[标签]`,标签即可靠检索键 —— 精确查表优于语义召回。
- V2 是**连贯叙事**:把一整段人格叙事切成向量块、按 top-k 拼回来,会把
  「完整自洽的一段过往」打散成**拼贴**,反而破坏角色稳定(与抗 OOC 目标相悖)。
  V2 的正确姿势是**按主题/维度整块加载**。

### 3.3 v0.1 硬上向量,代价远大于收益
- 需要 embedding(本地吃资源 / API 花钱 + 数据出境);
- 引入调用延迟、排队、缓存维护;
- 换回的检索精度提升,在这个体量下约等于零;
- 会拖慢最小闭环(v0.1 铁律:「GitHub 上的 v0.1 > 脑子里的 v3.0」)。

### 3.4 诚实地说:查表也有边界(写进报告,不藏)
- 对**模糊的、情绪化的、同义改写**的查询(如对抗式 case「你是不是怀念当年律者的力量」),
  纯子串查表**无法可靠映射**到正确的背景模块(它靠的是语义,不是字面重叠)。
- 这正是**向量 (语义召回) 的用武之地** —— 见下节「何时切向量」。

## 4. 接口与实现分离:留好「未来切向量」的通道(核心)

我们不为"现在"牺牲"将来"。做法是**定义抽象检索接口,让消费方只依赖接口**:

```
kb/retriever.py
├── BaseRetriever              # 抽象接口:query(text, top_k, domain) -> list[Retrieved]
│     ▲
│     ├── GuideRetriever         # V1:标签精确查表(当前默认,plain)
│     ├── LoreRetriever          # V2:主题/维度整块加载(当前默认,plain)
│     └── VectorRetriever(Stub)  # 未来语义召回实现的**占位契约**(未实现,标注清晰)
└── build_kb(mode)             # 门面:mode="plain"(默认)| 未来 mode="vector"
```

**关键点:消费方(Agent2 接入、将来的记忆系统)只调用 `BaseRetriever.query()`,
完全不感知底层是查表还是向量。** 因此未来切换是**纯内部替换,上层零改动**。

### 何时该切向量(演进判据)
当以下任一成立时,实现一个 `*VectorRetriever`(内部换 embedding + 向量库),`query()` 签名不动:
1. 单库条目涨到**千条量级**,查表漏召回开始明显;
2. 用户/评测 case 出现大量**语义模糊、同义改写**查询,子串查表覆盖不住;
3. 你需要跨多个异构知识源的**统一语义检索**。

### 一个架构级的注意(写进报告,防止未来踩坑)
- 对 **V1(工具知识)**,向量化是**纯增益** —— 攻略条目本就该能被语义模糊召回。
- 对 **V2(连贯叙事)**,即便上向量,也**应保持「整块」语义**:先按语义定位"该唤起哪段
  背景",再整块取出,而不是把块打散 top-k 拼贴。教训:连贯叙事的人格性经不起碎片化。

## 5. V2 两层设计:焊死的人格 + 外挂的叙事

这是与「角色卡焊死」的协同,不是冲突:

| 层 | 内容 | 存储 | 加载时机 |
|---|---|---|---|
| **核心人格(焊死)** | 性格锚点、语言风格、称呼规则、OOC 红线 | 角色卡 `data/character_card_v2.md`(进 system prompt) | 每次调用都在 |
| **详细叙事(外挂)** | 具体过往(家世/乐土/羁绊细节点) | V2 库 `kb/sources/v2_lore.txt`,经 LoreRetriever | 聊到相关话题时整块注入 |

- **焊死层**守住「让芽衣是芽衣」(抗渐进式 OOC 防线);
- **外挂层**在需要时按需带出详细记忆,避免每次调用都背一整段背景(省 token + 不漏关键情节)。
- **对抗式 case 不注入 V2** —— 评测要测的是纯人格防线的稳定性,喂背景可能反而给
  「怀念律者力量」这类陷阱递话。

## 6. 方案 A:评测阶段 framework 与检索的关系

v0.1 评测链路里,攻略 case 的 framework 仍是**指挥棒**(评测可控性优先):
- `framework` 来自 case —— 决定芽衣这次要答的方向(便于公平测口吻/人格);
- KB 检索器(V1)作为 Agent2 手边的**事实保险** —— framework 没覆盖的克制关系、
  武器归属等,芽衣能自己查到,不瞎编。

**演进留白(写进 README):**
- v0.1(现在):framework = case 提供(评测可控);
- 产品形态(B demo):framework 可由检索器接管 / 由 Agent1 依据真实知识生成 —— 那条
  "framework 由谁定"的接力棒,正是将来做长记忆 / 真产品的接口契约。

## 7. 与未来模块的接缝(长记忆 · 情绪衰减)

这套检索接口不只服务 V1/V2,它预埋了芽衣后续两大块:

```
Agent2 每次调用要喂的上文
├── 人格常量(焊死,角色卡)       ← 已在
├── 攻略知识(V1,检索)            ← 本模块
├── 背景叙事(V2,模块整块加载)     ← 本模块
├── 长记忆(phase2:她说过的关键事) ← 未来:MemoryRetriever 复用同一接口
└── 情绪/关系(phase2:账本折射)    ← 未来:状态层,决定上文带多强温度
```

- **长记忆本质就是一个检索器**:用户提话题 → 从记忆捞"我们之前聊过啥"。它和 V1 检索
  **是同一形状**,将来只需新增一个 `MemoryRetriever` insert 进同一接口,Agent2 零改动。
- **情绪衰减**是状态层,决定"这段上文该带多强温度",与检索正交 —— 但同样要读
  "该唤起哪段记忆",依赖同一个 query 通道。

> 所以本模块的**真正价值不是"攻略",而是把芽衣「需要时才知道什么」那根管子先立对了**。
> 今天接 V1/V2,明天长记忆往同一根管子里插,后天情绪状态决定温度,架构不用推倒重来。

## 9. 结论一句话

**先立接口、再上算法。** v0.1 用确定性查表(快、可复现、省成本)把链路跑通、把接口写对,
把"何时该切向量"的判据写进文档;等数据涨到千条 / 查询变模糊,实现一个 `VectorRetriever`
热切换 —— 上层一行不改。这才是**对"万一要进米哈游"最负责的适配性**:你展示的是
"懂接口与实现分离、懂何时上向量"的工程判断,而不是"盲目套了一个 Chroma"。
